# Long-running Ingestion on the current serverless stack

Researched 2026-11-15 for issue #34. Sources were first-party AWS and Cloudflare documentation, the pinned Terraform provider docs, and the checked-out repo. No infrastructure, credentials, or application code were changed, and nothing was load-tested. Vocabulary follows root `CONTEXT.md`: **Ingestion**, **Ingestion Method**, **Source**, **Provenance**.

## Recommendation

An Ingestion that makes one or more LLM calls should **not** run inside the `POST` request. The deployed path (Cloudflare → API Gateway HTTP API → Lambda → Data API) gives a request **30 seconds** at most, and that cap can't be raised [1][R1]. Part of that budget can go to waking Aurora from auto-pause, which typically takes about 15 seconds and 30 seconds or more after a day idle [9][R2]. The repo's existing Data API resume retry schedule already sleeps 31 seconds in total, which is longer than the whole gateway budget [R3].

For the first paste-text slice, the default to consider is:

1. `POST /ingestions` validates the pasted text. It persists the **Source** verbatim and an **Ingestion** in a `pending` state, then returns `202` with the Ingestion id. This is a fast request with a couple of Data API calls.
2. The API Lambda then invokes a worker **asynchronously** (`InvocationType: Event`) with only `{ ingestionId }`. The worker loads the Source, runs the LLM stage(s), and saves the Recipe and Provenance. It then marks the Ingestion `succeeded` or `failed` [5][6].
3. The SPA polls `GET /ingestions/:id` until the Ingestion reaches a terminal state.

Hide "run this Ingestion later" behind an application port, something like `IngestionRunner.start(ingestionId)`. Locally it runs the same pipeline in-process without awaiting, and in production it calls Lambda's async invoke. SQS or Lambda durable functions can replace the adapter later without changing the Ingestion lifecycle. These are design recommendations, not a tested implementation.

## Options for work beyond the request

Rough single-User scale assumption: about 100 Ingestions per month, each about 60 s of worker time at 512 MB, so about 3,000 GB-s. Lambda bills $0.20 per million requests and $0.0000166667 per GB-s on x86, with 1M requests and 400,000 GB-s free each month [15]. Worker compute is therefore about **$0.05/month before the free tier, and $0 within it**, for every option below. The differences are in orchestration cost, Terraform, and local development. ## Notes for the implementer

- **Lifecycle persistence is the real seam.** All of the async options need the same things: a persisted Ingestion with states (at least `pending`, `running`, `succeeded`, `failed`), an idempotent start, and a terminal write that includes failure reason and Provenance. Choosing async Lambda first doesn't block moving to SQS or durable functions later.
- **Set async retries deliberately.** The default of two retries on function error can multiply LLM spend and duplicate Recipes [6]. It's probably better to catch errors in the worker, record `failed`, and set `maximum_retry_attempts = 0`, or keep retries and enforce idempotency by Ingestion id. Add a DLQ or on-failure destination so a crashed worker can't leave an Ingestion stuck in `running` unnoticed. A sweep that marks stale `running` Ingestions as `failed` also works.
- **Worker timeout.** Set the worker's `timeout` above the sum of LLM call timeouts plus about 30 s for DB resume. Keep the API function at 30 s to match API Gateway [1][R1].
- **Don't hold Data API transactions across LLM calls** (3 min idle rollback) [7].
- **Wake the DB early.** The `POST` already wakes Aurora, so the worker usually starts warm. Status polls every 1–2 s cost Data API calls and keep the DB from pausing, so back off polling (for example, to 2–5 s) [9].

## Implications for decisions

**#38: Ingestion pipeline contract and lifecycle.** Input for the decision, not a decision:

- **Sync or async for the first paste-text slice.** The suggested default is **async**: `POST` creates the Ingestion (`pending`) and stores the Source verbatim, then returns `202 { ingestionId }`. A worker started through an `IngestionRunner` port runs the stages. The SPA polls `GET /ingestions/:id`, which also tells the User when an Ingestion finished or failed. Synchronous is only safe if #38 accepts that a cold DB plus one LLM call must fit in 30 s, and that it will have to be reworked once a second LLM call (Ingredient matching) or a slower Ingestion Method arrives [1][9].
- **Runner adapter.** In production, use **async Lambda invoke** of a worker with a longer timeout, explicit retry config, and a DLQ. Locally and in tests, run in-process. Move to SQS for buffering and redrive, or to **Lambda durable functions** for step checkpointing across multiple LLM calls, once photo or video Ingestion Methods make runs long or multi-stage. Step Functions and response streaming are poor fits for this stack (ASL/256 KiB; HTTP API can't stream) [4][20].
- **Lifecycle the contract must express.** Explicit states, including a terminal `failed` with a reason. An idempotent start keyed by Ingestion id, because Lambda async invocation can deliver an event more than once [6]. No transaction spanning stages [7]. Provenance written at the terminal transition.
