# Ingredient Line parsing and Ingredient matching

Researched 2026-11-15 for #33 (map #31). Sources are first-party: project repos and docs, package registries, papers, dataset licence pages, and live queries against the FDC and Wikidata APIs and the Open Food Facts taxonomy files. No application code was changed. Vocabulary follows root `CONTEXT.md`: an **Ingredient** is a shelf-level catalog entry shared by all Users, an **Ingredient Line** is one Recipe's use of it as written, and a **Preparation** belongs to the line.

## Recommendation

There are two separate problems. Treat them separately.

1. **Parsing an Ingredient Line** into amount, unit, Ingredient name, and Preparations: do it in the same LLM call that extracts the Recipe, returning schema-constrained JSON. Validate that JSON with Zod in TypeScript, and use a small deterministic TypeScript normaliser for quantities and units. No maintained JS/TS library splits the Ingredient from its Preparations. The best open dedicated parser for that is Python (`ingredient-parser-nlp`). It is a credible fallback or offline benchmark, but it is not needed for v1. [1][2][5][6]
2. **Matching to a canonical Ingredient**: retrieve candidates, then let the model choose. Retrieve a small candidate set from the global catalog with lexical and synonym search, then have the LLM either pick one candidate or propose a new Ingredient. TypeScript code makes the final decision, enforcing the policy and recording the result. Published systems that do this report the best robustness. Their main failure mode is minting near-duplicates ("dextrose" next to "glucose"), and policy has to prevent that. [9][10]
3. **Seeding the catalog**: the Open Food Facts ingredients taxonomy fits shelf-level identity best. It has red onion as a child of onion, synonyms, many languages, and Wikidata IDs, but it is under ODbL (attribution and share-alike). Wikidata (CC0) and USDA FDC (US public domain) are licence-free anchors. FoodOn (CC BY 4.0) is too granular to use directly as a shelf catalog. [12][13][14][15][16][17]

Takeaways:

- Quantities and units are a solved, deterministic problem in TypeScript. Even if the LLM returns numbers, keep a TS normaliser for fractions, ranges, and the unit vocabulary as the canonical form, and to cross-check what the model returns. [5]
- Separating the Ingredient name from its Preparations is the hard part. Only the Python CRF/ML parser and LLMs do it. A Preparation vocabulary already exists to validate against. The Open Food Facts `ingredients_processing.txt` taxonomy has 262 English entries, including chopped, finely chopped, diced, minced, and shredded. [17]
- The Python parser's figures are measured on its own label scheme and test split. They are not a head-to-head benchmark against LLMs, and none was found.

## (b) Matching to a canonical shelf-level Ingredient

| Approach                                                                      | Notes and figures                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Exact or normalised string plus synonym table**                             | Deterministic and auditable, and it handles "red onions" → red onion. It cannot judge new or unusual wording. Preparations must be stripped first, which is a parsing problem.                                                                                                                                                                                                                                                                                                                                                                                            |
| **Lexical and semantic ranker fusion** (`ingredient-parser` foundation foods) | Matches names to USDA FDC entries offline. Steps: normalise and stem; apply a hand-built override list; rank with BM25; rank with uSIF over recipe-trained GloVe embeddings; if the two disagree, add a fuzzy ranker; fuse the scores; reject weak or near-tied matches. Parsing is about **20x slower** with it on. The page gives **no accuracy figure** and says its significance threshold is "unlikely to be perfect". It targets nutrient records rather than shelf items. **Python.** [4]                                                                          |
| **Fine-tuned LLM entity linker** (FoodSEM)                                    | Up to 98% F1 on some FoodOn, SNOMED-CT, and Hansard datasets. [10] It is tied to the ontology version it was trained on (see next row).                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Retrieve, then LLM judge** (FoodOntoRAG)                                    | Retrieves BM25 top-15 and MiniLM embedding top-15 candidates and merges them. A selector LLM applies "exact match" and "specificity" rules, a scorer LLM gives a confidence score, and low confidence triggers synonym retries. Scored **90.7% Acc@1 on an Open Food Facts set vs 36.9% for fine-tuned FoodSEM**. On CafeteriaFCD it scored 57-60% raw. After adjudication, 76.9% of the flagged "errors" turned out to be valid alternative terms, for example "onion" fitting both an ingredient class and a taxon. The test sets are small: 119 and 948 mentions. [11] |
| **Retrieve, then LLM picks or proposes new** (branded-food pipeline)          | The fine-tuned model matched 84.4% exact on mapping (experts: 81.5%). Parsing followed by mapping fell to 50.0% because errors compound. The main failure was the model **adding "dextrose" when "glucose" already existed**. [9]                                                                                                                                                                                                                                                                                                                                         |

Takeaways:

- The open-world shape, where unknown Ingredients are created for everyone, matches the "pick a candidate or propose a new term" pattern in [9] and [11]. Both papers show that the real risk is **catalog drift through near-duplicates** and ambiguity about granularity, not wrong picks. Shelf-level identity ("red onion" ≠ "yellow onion", but "diced red onion" = red onion) is exactly the kind of specificity rule [11] writes into its selector prompt.
- Candidate retrieval does not need embeddings. FoodOntoRAG still uses BM25 alongside embeddings, and the `ingredient-parser` matcher trusts the lexical ranker when the semantic one has no vocabulary. [4][11] Aurora PostgreSQL 18.4, which the repo runs, supports `pg_trgm` 1.6 and `pgvector` 0.8.2. [18][R1] Map #31 puts embeddings and vector search out of scope, so trigram and synonym retrieval is the v1 option that fits. Adding pgvector later is possible without changing engines.
- The published numbers come from nutrition and ontology linking, not from linking recipes to a shelf catalog. Expect to build a small labelled set of your own Ingredient Lines to evaluate against.

A defensible seed is a hand-curated starter list of common shelf Ingredients. Store an optional `offTaxonomyId` or `wikidataId` on each Ingredient as an anchor rather than bulk-importing a dataset. Linking to CC0 Wikidata IDs carries no licence obligation. Bulk-importing Open Food Facts taxonomy entries likely makes the catalog an ODbL derivative.

## Python flags

- Python only: the NYT tagger (archived), `ingredient-parser-nlp` with its FDC foundation-food matcher, the research taggers, and FoodSEM, FoodOntoRAG, and similar code.
- AGENTS.md allows Python for extraction and ML. If a Python parser were used, it should sit behind the Ingestion boundary as a stateless extractor whose output TypeScript validates with Zod. Matching policy and catalog writes would stay in TypeScript.
- Approaches with no Python: an LLM over HTTP, `parse-ingredient` for quantities and units, Postgres `pg_trgm`, and hand-curated or taxonomy-derived synonym data.

## Implications for decisions

These are inputs to the decisions, not the decisions themselves.

- **#36 Ingredient Line structure.** Recommended default:
  - Keep the original wording.
  - Amount as `{ quantity, quantityMax? }` to allow ranges, plus a canonical unit ID from a TS unit vocabulary, or null for unitless lines ("2 eggs").
  - `ingredientId`.
  - An ordered list of Preparation strings, optionally normalised against a small Preparation vocabulary.
  - A free-text `note`/comment for leftovers such as "plus more to taste" or "about 2 large".
  - Optionally size and purpose ("for garnish"), because `ingredient-parser` shows these recur often enough to deserve their own labels. [2]

  The LLM returns these fields during Ingestion. TS validates and normalises them. Lines that fail validation keep their wording and leave the structured fields null rather than failing the whole Ingestion.

- **#37 matching and creation policy.** Recommended default:
  1. Normalise the name (case, plural form, Preparations stripped).
  2. Try an exact match on name or synonym.
  3. Otherwise retrieve the top N catalog candidates with `pg_trgm` and synonyms.
  4. Ask the LLM to choose one candidate ID or propose `new` with a canonical shelf-level name, applying a written specificity rule (variety and colour are kept; Preparation, size, and state are dropped).
  5. TS accepts the result. A new Ingredient is created only after a final exact or synonym check, and the model's alternate names are recorded as synonyms.
  6. Record the decision and candidates in Provenance (#39) so wrong matches and duplicate merges, listed as unspecified in #31, can be fixed later.

  Seed with a small curated list. Optionally anchor Ingredients to Wikidata IDs (CC0), and decide separately whether ODbL obligations are acceptable before importing Open Food Facts taxonomy data.

- **New questions surfaced:** whether ODbL share-alike is acceptable for the global catalog; how to handle vague names like "chicken" and "onion" under the specificity rule (already noted in #31); and whether to build a small labelled evaluation set of Ingredient Lines to measure parsing and matching before and after model changes (relevant to #32).
