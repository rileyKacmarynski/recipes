# Ingestion orchestration, runtimes, push notifications, and web page structured data

Researched 2026-11-17 for issue #48, which blocks #38. Sources were first-party AWS, Cloudflare, Anthropic, OpenAI, Google, and schema.org documentation, the source code and package metadata of the libraries named, and the checked-out repo. Nothing was deployed, load-tested, or tried hands-on. Claims the sources don't settle are marked **unverified**.

Vocabulary follows root `CONTEXT.md`. **Step** means a Recipe instruction, so pipeline parts are called **stages** here. The stage names follow #38's working contract: `prepare` (Source → Extraction Input), `extract`, `match` (Ingredients), and `save`.

Constraints already fixed by #38: per-stage retry, resume from the failed stage, per-stage visibility, and per-stage runtime/language. The API publishes an event and contains no pipeline code. The User is notified through an API Gateway WebSocket API. TypeScript owns business logic, and Python is only for extraction/ML. Region is us-east-1, AWS provider 6.61.0, single-User scale. Prior research for #34 covered the 30 s request limit and async workers [49].

## Recommendation

These are suggested defaults, offered as input to #38. They are not decisions.

1. **Runtimes.** Photos don't need a separate OCR stage. A vision LLM reads the text in the image directly, so `prepare` should only normalize the image (apply rotation, downscale, re-encode) [1]. Video is the one Ingestion Method that needs Python. Its download stage runs yt-dlp, ffmpeg, and a JavaScript runtime, which fits a **container-image Lambda** (10 GB image, up to 10 GB `/tmp`, 15 min) [4][7]. Transcription should be a **managed API** called from TypeScript, either OpenAI `gpt-transcribe` or Amazon Transcribe [2][3]. Self-hosted Whisper isn't worth running on Lambda.
2. **Orchestration.** Use a TypeScript **Lambda durable function** as the orchestrator. Each stage is a durable step, or a `context.invoke` of a separate Lambda in another runtime, such as the Python download stage [12][13]. Each stage's output is stored **by reference** in Postgres/S3 and recorded in an app-owned stage table. That table gives the User per-stage visibility and makes "resume from the failed stage" work. A closed durable execution **can't be redriven**, so a resume starts a new execution that skips stages whose outputs are already recorded [14]. **Step Functions Standard** is the close alternative. It ships native redrive from the failed state and a per-state console, but it moves orchestration into ASL, has weak local dev, and caps payloads at 256 KiB [18][19][20].
3. **Hand-off.** The API writes the Source and the `pending` Ingestion in one transaction, then calls EventBridge `PutEvents` and checks `FailedEntryCount` [22]. Treat the `pending` row itself as the outbox. A sweep re-publishes `pending` rows older than a threshold. Run it on requests that already wake Aurora rather than on a tight schedule, so it doesn't stop auto-pause [27][49]. The consumer starts with the durable execution name set to the Ingestion id, which makes a duplicate start harmless [14].
4. **Push.** Create a separate WebSocket API on its own hostname. A WebSocket custom domain can't share a hostname with the HTTP API [34]. Proxy that hostname through Cloudflare and add it to the existing Access application. A Lambda REQUEST authorizer on `$connect` validates the `Cf-Access-Jwt-Assertion` header with the existing API auth code [31][37]. **Whether Access applies to the upgrade request and forwards that header is unverified.** Spike it first, and fall back to a one-time ticket in the query string. Store connection ids in Postgres. Push from the pipeline with `PostToConnection`, and delete the row on `GoneException` [30]. Keep `GET /ingestions/:id` as the resync path, because connections drop after 10 min idle and always after 2 h [28].
5. **Web page structured data.** Yes, the contract should allow it. A web-page `prepare` should be able to hand the shared stages the page's schema.org `Recipe` node alongside the text and images. When it is present, `extract` can map most fields directly or with a cheaper model. One gap still needs page text or an LLM: `recipeIngredient` is a flat list, so it doesn't carry Sections [39][44]. Keep the fetched HTML as part of the Source [R7].

### Suggested default and why

Use **durable functions**, with an app-owned stage table that the orchestrator writes at each stage boundary:

- The stage table (for example `ingestion_stage(ingestion_id, stage, status, attempt, output_ref, error, started_at, finished_at)`) is needed anyway. It drives the WebSocket progress pushes and `GET /ingestions/:id`. Neither orchestrator's history is something to show the User.
- With stage outputs stored by reference, both "resume from the failed stage" and Step Functions-style redrive reduce to the same thing: start a new execution, and skip every stage whose output is already recorded. Durable executions can't be redriven after they fail [14], so this table is what provides resume.
- The flow stays TypeScript and is unit-testable [11][17]. Step Functions' main advantages are native redrive and the console graph [19]. Both matter less once the stage table exists, and its 256 KiB limit and unsupported local emulator cost more here [18][20].

**Choose Step Functions instead** if #38 wants redrive without writing the skip-completed-stages logic, or wants AWS's per-state console as the main operator tool.

**Open interaction with #38.** #38's working notes say "Retrying creates a new Ingestion on the same Source." "Resume from the failed stage" implies the opposite: continuing the _same_ Ingestion. #38 should say which is which. One reading is that a User-initiated retry creates a new Ingestion, while an operator or automatic resume continues the same one with `attempt + 1`.

### Hand-off: avoiding or detecting a lost publish

Writing the row and publishing the event is a dual write. If the process dies between commit and `PutEvents`, the pipeline never hears about the Ingestion [27]. Options:

| Option                                                    | How                                                                                                                                                                                                                                                                                           | Trade-off                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Publish after commit, check the result                    | `PutEvents` can partially fail and still return HTTP 200, so check `FailedEntryCount` and the per-entry `ErrorCode` [22].                                                                                                                                                                     | Catches service-side rejects. It doesn't catch a crash between commit and publish.                                                                                                                                                                                                                                          |
| **Ingestion row as the outbox, plus a sweep** (suggested) | The `pending` row (with `published_at`/`publish_attempts`) is the outbox record, written in the same transaction as the Source [27]. A sweep re-publishes `pending` rows older than N minutes. The consumer is idempotent through the durable execution name or a conditional claim [14][27]. | AWS's outbox guidance uses a polling relay [27]. A frequent schedule would keep Aurora awake, because each Data API call resumes it and it stays up at least 300 s after [49]. Run the sweep **on requests that already touch the DB** (`POST /ingestions`, `GET /ingestions…`), plus at most an infrequent scheduled pass. |
| Separate outbox table + relay                             | The textbook form [27].                                                                                                                                                                                                                                                                       | It adds a table and duplicates what the `pending` state already says.                                                                                                                                                                                                                                                       |
| CDC                                                       | AWS's CDC example uses DynamoDB Streams [27].                                                                                                                                                                                                                                                 | Not available with Aurora via Data API on this stack. Not pursued.                                                                                                                                                                                                                                                          |

Delivery side: EventBridge retries a failed target and can send events it couldn't deliver to an SQS DLQ. Some errors, such as missing permissions, go straight to the DLQ without retry [24]. Its retry policy is configurable up to 185 attempts and 24 h [23]. AWS also launched a new "Custom Event Bus" type with different pricing and quotas [23][25]. Whether provider 6.61.0 models it is **unverified**, so the classic bus (`aws_cloudwatch_event_*`) is the safe default. Classic custom-event ingestion costs $1.00 per million events, with each 64 KB chunk billed as one event [25]. That's $0 in practice.

## 3. Pushing Ingestion progress through an API Gateway WebSocket API

### Limits and costs

| Item                               | Value                                                                                                                                                                                                                                                      |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Connection duration / idle timeout | **2 h / 10 min**. Neither can be changed [28].                                                                                                                                                                                                             |
| Message / frame                    | 128 KB message, 32 KB frame. A larger frame closes the connection with code 1009 [28]. Progress events should be small (`{ ingestionId, stage, status }`).                                                                                                 |
| Integration timeout                | 50 ms to 29 s, fixed [28]. This matters if `$connect` writes to Aurora while it is paused.                                                                                                                                                                 |
| New connections                    | 500/s per account. There's no quota on concurrent connections [28].                                                                                                                                                                                        |
| Authorizer                         | Lambda REQUEST authorizer, on `$connect` only. It can read headers and query strings, and its result is limited to 8 KB [28][31]. Authorization "is applied to the entire API" because `$connect` gates every connection [33].                             |
| `$disconnect`                      | Best-effort. Delivery isn't guaranteed [32].                                                                                                                                                                                                               |
| Custom domain                      | Regional only, TLS 1.2. **A domain mapped to a WebSocket API can't also map an HTTP API** [34], so it needs a new hostname and a new ACM SAN. Today's certificate covers only the web and API hostnames [R3].                                              |
| Cost                               | $1.00 per million messages (metered in 32 KB blocks, with ping/pong not metered) and $0.25 per million connection-minutes. The free tier is 1M messages and 750k connection-minutes per month for 12 months [29]. At this scale, that's under $0.01/month. |
| Cloudflare                         | WebSockets work on all plans. Cloudflare restarts can drop connections, and it recommends keepalives [35]. The binding idle limit is API Gateway's 10 min [28].                                                                                            |

### Behind Cloudflare Access: authenticating and tying a connection to a User

- The browser `WebSocket` constructor takes only a URL and subprotocols, so it can't send custom headers. Cookies are sent on the handshake under Fetch rules (credentials mode "include") [38]. The SPA therefore can't pass the Access JWT as a header the way `fetch` can. The connection has to be authenticated by the `CF_Authorization` cookie, a query-string token, or a subprotocol value.
- Access issues a `CF_Authorization` cookie per protected hostname. For multi-domain applications, it can issue cookies for the other domains after one sign-in [36]. Cloudflare adds `Cf-Access-Jwt-Assertion` to origin requests and recommends validating that header rather than the cookie [37]. The API already validates that header [R4].
- **Unverified.** No Cloudflare page reviewed says that a hostname-based Access application enforces Access on a WebSocket upgrade and forwards `Cf-Access-Jwt-Assertion`. Cloudflare's Workers docs do say that _Worker-level_ Access policies don't support WebSockets, and they recommend a hostname-based Access application instead (seen in a search excerpt of the Workers Access page, not read in full) [46]. The application's current `same_site_cookie_attribute = "none"` and `http_only` cookie settings [R2] should allow a cross-subdomain handshake to carry the cookie, but that is also **unverified**.

**Suggested default (spike first):**

1. Add a `recipes-ws.rkac.dev` hostname: a proxied Cloudflare record, a destination in the existing Access application, and a Regional WebSocket custom domain [34].
2. The `$connect` route uses a REQUEST authorizer with identity source `route.request.header.Cf-Access-Jwt-Assertion`. It reuses the API's Access JWT validation to resolve the User, and passes `userId` in the authorizer `context` [31].
3. **Fallback if the spike fails:** the SPA calls `POST /ws-tickets` on the existing HTTP API, which is already Access-protected. It gets a short-lived, single-use ticket and connects with `?ticket=…`. The authorizer checks the ticket. The trade-off is that the ticket appears in the URL, and so possibly in access logs.

### Where connection ids live and how a Lambda pushes

- **Store:** a Postgres table such as `ws_connection(connection_id, user_id, connected_at, expires_at)`, written by `$connect` and deleted on `$disconnect`, which is best-effort [32]. Also delete on `GoneException` and expire after 2 h [28][30]. AWS notes that the connection id's "length and format might change", so store it as text [32]. The risk is that `$connect` writes to a paused Aurora, which can take 15–30 s or more to resume, against a 29 s integration timeout [28][49]. In practice the SPA's own requests have usually woken the DB already, and the client should retry the connect with backoff. DynamoDB would avoid this, but it adds a datastore. Not suggested.
- **Push:** the pipeline (a TS `notify` helper called at each stage boundary) calls `PostToConnection` through `@aws-sdk/client-apigatewaymanagementapi`. It needs IAM `execute-api:ManageConnections` and SigV4 [30]. One User may have several tabs open, so it fans out to all of the User's connections.
- **Management endpoint (unverified).** The documented endpoint is `https://{api-id}.execute-api.{region}.amazonaws.com/{stage}/@connections/{id}`, or the custom domain without the stage [30]. Two things are open. The first is whether `disable_execute_api_endpoint = true` (the ADR 0002 posture [R5]) also disables the management API. The second is that calling through the custom domain would pass through Cloudflare Access, which would need a service token. The suggested default is to **leave the default endpoint enabled on the WebSocket API** and rely on the `$connect` authorizer. ADR 0002 already treats disabling it as defense in depth, not the control [R5]. Record that in an ADR amendment.
- **Resync:** after any reconnect, the SPA calls `GET /ingestions/:id`. The WebSocket is a latency optimization, and the persisted lifecycle stays the source of truth.

### Local dev

No AWS-provided local emulator for WebSocket APIs was found (**unverified** whether SAM supports one). Hide pushes behind a `ProgressNotifier` port. In development, the adapter can push over a plain WebSocket served by the local dev process. In tests, an in-memory fake records what would have been pushed. The authorizer and the connection-store logic are plain functions you can test with Vitest.

## 4. Structured recipe metadata on web pages

### Coverage

- Google requires `name` and `image` for recipe rich results. It recommends `recipeIngredient`, `recipeInstructions`, `recipeYield`, `prepTime`/`cookTime`/`totalTime`, `description`, `author`, `nutrition`, and others [40]. It accepts JSON-LD, Microdata, and RDFa, and recommends JSON-LD [41]. That search incentive is the main reason recipe sites publish the markup.
- Web Data Commons' Dec 2024 extraction (from Common Crawl) found schema.org `Recipe` on **37,304 hosts and 2.75 M URLs** [42]. No primary source was found for the _share_ of recipe sites that embed it. "Most major recipe sites" is a widely held belief, but **unverified**.
- recipe-scrapers (Python) lists 755 supported cooking sites [43]. Its site-specific scrapers mostly sit on top of the schema.org parser, which is indirect evidence that the markup is common.

### Bot blocking when fetching from Lambda

- Cloudflare's AI Crawler and Agent policies sort traffic into Search, Agents ("acting in real time on a person's behalf"), and Training. The developer docs say all three default to Allow for new domains [46]. A Cloudflare changelog and blog post say that from 2026-09-15, new domains block Training and Agent traffic on pages with ads [46]. **The sources conflict, and which default applies to a given recipe site is unverified.** Ad-supported recipe blogs are exactly the "pages with ads" case.
- Bot Fight Mode, available on the Free plan, challenges traffic that matches known bot patterns. WAF rules can't bypass it [47]. A server-side `fetch` can't solve a challenge. Cloudflare marks challenge responses with `cf-mitigated: challenge` and `text/html` [48].
- Whether Lambda's AWS egress IPs are routinely challenged by recipe sites is **unverified**. Spike it against a handful of real sites before building the Method.
- **Suggested handling.** Send an honest User-Agent. Detect `cf-mitigated: challenge` and other 403/503 bot pages, and fail with a specific reason. #38's list has `unreadable`, and a `blocked_by_site` reason may be worth adding. Offer pasting the text as the fallback. A later "send page from the browser" path, such as a share sheet or extension posting rendered HTML, avoids server-side fetching, but is out of scope here.

### Answer to the contract question

**Yes, let a web-page `prepare` hand the shared stages structured data alongside text and images.** Text plus images would _work_, because an LLM can re-read the page. But it throws away data the site has already structured, and it re-introduces errors in fields that map directly. A suggested Extraction Input shape:

```ts
type ExtractionInput = {
  text: string // readable page text (or pasted text)
  images: ImageRef[] // photos, video frames
  structured?: { kind: 'schema.org/Recipe'; recipe: unknown } // the selected Recipe node, as found
}
```

- `prepare` selects the Recipe node (handling `@graph`, `mainEntity`, and array `@type`). It fails with `multiple_recipes` if there are several distinct ones. It keeps the fetched HTML with the Source, as #38's "verbatim covers what was fetched" requires [R7]. Store the HTML by reference (S3 or a large column). A page can exceed the Data API's 1 MiB response limit and the 1 MB async payload [7][49].
- `extract` stays one stage with one output schema. With `structured`, it can deterministically map name, Steps (and Sections from `HowToSection`), Yield, times, and the Ingredient Line wording, after decoding entities and stripping tags. That leaves one cheap LLM call to assign Ingredient Lines to Sections using the page text, because schema.org has no ingredient sections [39][44]. Without `structured`, it uses the full LLM path. Ingredient matching is a separate stage either way.
- **Whether to adopt a parser:** both recipe-scrapers ports are MIT. The Python one is mature. The TS port fits the "TypeScript owns logic" rule but is young [43][45]. The node-selection and normalization logic is small. The suggested default is to write it in TS against fixtures, using recipe-scrapers' handling as the checklist of quirks [44], and to revisit the TS port once it has matured.

## Notes for the implementer

- **Stage outputs by reference.** Every orchestration option has a payload ceiling: 256 KiB for Step Functions, 1 MB for durable operations, async invoke, SQS, and EventBridge, and a 1 MiB Data API response [7][18][22][26]. Pass `{ ingestionId, stage, outputRef }`, not content.
- **Durable versioning.** Durable executions are pinned to the function version that started them. Ship stage logic as numbered versions or an alias, never `$LATEST`. Lock the SDK major version [9][13].
- **Idempotency everywhere.** Use the execution name as the Ingestion id (plus attempt) [14]. Make the `pending → running` claim conditional. Write each stage's output with an upsert keyed by `(ingestion_id, stage, attempt)`. Steps run at least once [14].
- **No transactions across stages** (the 3 min Data API idle limit) [49]. Only `save` is one atomic write, as #38 already decided.
- **Failure surfacing.** Use the durable function's DLQ, since it doesn't support Lambda destinations [13]. Add an EventBridge rule on `Durable Execution Status Change` = `FAILED`/`TIMED_OUT` that marks the Ingestion `failed` if the orchestrator didn't [15].
- **WebSocket is best-effort.** Missing a push must never strand the UI, so it needs resync through `GET`. Push only stage transitions, not tokens.

## Implications for #38

Input for the decision, not a decision:

- **Contract.** Extraction Input = `text` + `images` + optional `structured` (schema.org Recipe node). Web-page `prepare` fills `structured` when the page has it. Photo `prepare` normalizes images and adds no OCR. Video `prepare` is a Python container stage that returns S3 references to audio and frames, followed by a TS transcription stage.
- **Orchestrator.** A TS durable function, plus an app-owned `ingestion_stage` table that holds stage outputs by reference. Resume means a new execution that skips recorded stages. Step Functions is the alternative if native redrive is preferred over writing that skip logic.
- **Retry semantics.** Decide whether "resume from the failed stage" continues the same Ingestion (`attempt + 1`) while a User retry creates a new Ingestion. The current notes say only the latter.
- **Hand-off.** Commit the Source and the `pending` Ingestion, then `PutEvents` and check `FailedEntryCount`. The `pending` row is the outbox. A sweep that runs on DB-touching requests re-publishes stale `pending` rows. Starts are idempotent by execution name or conditional claim.
- **Failure reasons.** Consider `blocked_by_site` for web pages served a bot challenge. Map multiple schema.org Recipe nodes to `multiple_recipes`.
- **Push.** A WebSocket API on its own hostname, inside the Access application, with a `$connect` authorizer validating the Access JWT. Spike this. The fallback is a one-time ticket. Connection ids go in Postgres. Pushes happen at stage transitions, with resync through `GET /ingestions/:id`. Record any change to ADR 0002's endpoint posture in an ADR.
