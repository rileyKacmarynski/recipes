# Deployed-environment test identity and data isolation

Researched 2026-11-15 against first-party documentation and the checked-out repo, for [#45](https://github.com/rileyKacmarynski/recipes/issues/45) (feeding [#46](https://github.com/rileyKacmarynski/recipes/issues/46)). No infrastructure, credentials, or application code were changed, and no live authentication was attempted. Vocabulary follows `CONTEXT.md` (User, Recipe, Ingredient, Ingredient Line, Ingestion).

## Recommendation

Give the deployed test a **dedicated synthetic User**. It is created and found through the same provider + subject path that [#35](https://github.com/rileyKacmarynski/recipes/issues/35) settled for humans, keyed by `cloudflare-access-service` + the verified service-token `common_name`. Isolation then comes from the ordinary ownership rule ("Recipes are visible and editable only by their owning User"), not from a route allowlist. The synthetic User can write and read its own Recipes and can never see another User's. Clean up with a **sweep-then-create-then-delete** pattern scoped to that User's id, so a failed run is repaired by the next one.

The one place this isolation does not hold is the **global Ingredient catalog**. Any write path that can create Ingredients (Ingestion, or Ingredient Lines that are matched or created) writes data every human User sees. Until there is a test-tenancy story for Ingredients, deployed tests should not run Ingestion or create new Ingredients. [R4][9]

This is input to #46, not a decision.

## Cloudflare `sub` for human identities: what is documented

Cloudflare's application-token reference defines the identity-token `sub` as follows: "The ID of the user. This value is unique to an email address per account. The user would get a different `sub` if they are removed and re-added to your Zero Trust organization, or if they log into a different organization." The example value is a UUID (`7335d417-…`). For service tokens, `sub` "contains an empty string" and `common_name` is "the Client ID of the service token (`CF-Access-Client-Id`)". [1]

No per-session or per-token variation is described. [1] Cloudflare also states that a user record "cannot be deleted or archived". [3]                                                                                                                                                                                                                                                                                                           |
| `sub` stays the same across IdPs (OTP vs Google) | **Implied, not stated**      | The docs scope `sub` to the email address and never mention the IdP or login method. Per the wording, the same email through OTP or Google should give the same `sub`. No Cloudflare page says so explicitly, and none says the opposite. OTP is documented as configurable "simultaneously" with another IdP, and its users are identified by email. [1][2] Treat this as unverified until checked live: log in once with OTP and once with Google using the same email, and compare `sub` (or `user_uuid` from `/cdn-cgi/access/get-identity`). [1] |
| `sub` survives removing the user from the org    | **Contradicted**             | Removing and re-adding gives a new `sub`. [1] Removing a user frees their seat. [3] So "freeing a seat" for the owner would orphan their User under the #35 key.                                                                                                                                                                                                                                                                                                                                                                                      |

Implication for #35's provider + subject key: it holds across sessions and, by Cloudflare's wording, across login methods. It does not survive org membership churn. Email is refreshed on each login and stored for display only, which is the right fallback signal for a manual re-link if `sub` ever changes. Auto-linking by email would be a separate decision.

## Getting through Cloudflare Access

- **Mechanism (unchanged from the prior note):** send `CF-Access-Client-Id`/`CF-Access-Client-Secret` and attach a **Service Auth** policy. Without that action, "Access will prompt for an identity provider login". Strict service-token auth returns 401/403 instead of redirects, and only Service Auth policies authorize those requests. [4] The origin receives a signed JWT with `common_name` and empty `sub`. [1] The repo already does this. [R1][R3]
- **Rotation keeps the identity stable.** Rotating a token generates a new secret but "the Client ID remains the same". [4] So `common_name` is a durable key for a synthetic User across rotations. Replacing the token entirely, rather than rotating it, would create a new synthetic User. That is harmless if the old one's data was swept, but worth a one-line runbook note.
- **Mapping to a synthetic User.** `cloudflareAuthProvider` already routes any JWT carrying `common_name` down a separate branch, rejects any Client ID other than `CLOUDFLARE_SMOKE_CLIENT_ID`, and returns `{ provider: 'cloudflare-access-service', subject: common_name }`. [R1] Under #35 that pair would simply feed the same find-or-create-User path. Human subjects are UUIDs and service subjects are `<client-id>.access`, and the provider also differs, so the two cannot collide. [1] Keep the explicit Client ID allowlist so that any other service token in the org cannot mint Users.
- **Edge scoping is optional.** Access apps can protect specific paths, and "the more specific rule takes precedence". [8] A path-scoped app could narrow the token at the edge, but it would carry its own audience tag that the API would also have to accept. The prior note and ADR 0004 already concluded that the API must enforce restrictions regardless, since the web and API hostnames share one app. [R5]
- **Credential hygiene** stays as in ADR 0004. AWS's canary guidance makes the same points: don't log secrets or sensitive headers or bodies, and keep execution roles scoped down. [7]

## What could still leak real User data

1. **The global Ingredient catalog.** Ingredients are "shared by all Users; one first seen during Ingestion is added for everyone". [R4] A test Ingestion could add junk Ingredients (for example "smoke-test flour") to everyone's catalog. Matching would also read the global catalog, which is fine because the catalog is not private User data. Deleting test-created Ingredients risks deleting something a real Ingredient Line later matched. Options: keep Ingestion out of deployed tests; only ingest a fixed Source whose Ingredients already exist (brittle, since an LLM may still propose new ones); or add a tenancy/origin marker on Ingredients (Uber's tenancy column). [9]
2. **Ingestion cost and side effects.** Every deployed Ingestion is a paid LLM call and an async worker invocation (#32, #34). Run it on demand, not on every deploy.
3. **Unscoped queries.** Isolation through a synthetic User is only as good as the owner filter on every Recipe query. The existing app-level Vitest tests (`app.request`) are the right place to assert that a second User cannot list or fetch the first User's Recipes. Uber notes that range queries specifically must carry the tenancy filter. [9]
4. **Logs and metrics.** Uber tags test traffic so it can be filtered and does not skew alerts. [10] Here the structured identity (`provider`) is enough to filter synthetic traffic. No log line should print Recipe contents. [7]

## Implications for decisions (#46)

**Recommended default (for the user to accept or change):**

1. **Synthetic User via the normal User path.** Map a verified, allowlisted `common_name` to a User keyed by (`cloudflare-access-service`, `common_name`) through the same find-or-create code as human logins. There is no email, or a clearly synthetic display value. No special-cased auth mode is added, which matches #35's "no special-cased dev mode" stance.
2. **Drop the route allowlist; rely on ownership.** The synthetic User may use any Recipe route. Per-User ownership guarantees it sees only its own Recipes. Keep exactly one guard: the synthetic User may not trigger Ingestion or create Ingredients (403), until a decision is made about Ingredient tenancy.
3. **Smoke flow per deploy:** sweep the synthetic User's Recipes → `POST /recipes` → `GET` it back by id → appears in `GET /recipes` → delete it → list is empty. This needs a Recipe delete path (or a smoke-only cleanup that calls the same domain delete). Fail the deploy on any step except a cleanup error, which should be reported and is repaired by the next sweep.
4. **Before relying on the #35 key,** verify `sub` live with the owner's email through OTP and through any second IdP. Add a runbook note that removing the owner from the Zero Trust org changes `sub`. [1]

**What would change in ADR 0004 (supersede or amend):**

- "Do not require seed data or write test records" → the smoke check writes and deletes Recipes owned by a dedicated synthetic User, sweeping first.
- "That identity can only access `GET /recipes` … cannot write recipes or access `/me`" → the identity is a normal User for authorization purposes, bounded by ownership. Its remaining hard restriction is no Ingestion or Ingredient creation.
- "Normal user authorization is unchanged" → authorization is now per-User ownership (from #35), and the service identity goes through it rather than around it.
- Unchanged: dedicated expiring token, Service Auth policy, explicit Client ID allowlist, no anonymous or developer fallback, no JWT echo, credential and state hygiene, failure fails the deploy.

**Alternatives the user may prefer:**

- **Keep read-only** (status quo, with `GET /recipes` returning the service identity's own, empty, list after #35). This is lowest risk, but writes stay untested in production and the check proves less once the list is always empty.
- **Separate staging environment** for write and Ingestion tests (Stripe-style full separation [12]). This gives the strongest isolation, including Ingredients, but costs a second Aurora cluster and deploy role, which ADR 0002 anticipates but doesn't build.

**Open questions for #46:**

- Do deployed tests ever need to exercise Ingestion? If so, choose between Ingredient tenancy, a staging environment, or a fixed known-Ingredient Source.
- Does Recipe v1 include delete? Sweep-first cleanup depends on it.
- Should a changed `sub` with a matching email re-link to the existing User, or is that a manual operation?
